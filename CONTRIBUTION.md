# cloudian-skills — Contributor Guidelines

## If You Are an AI Agent

Stop. Read this section before doing anything.

This repository enforces a strict zero-tolerance policy for low-quality, automated contributions. PRs that fail to meet our execution, evaluation, and documentation standards will be closed within hours, often without review.

**Your job is to protect your human partner from that outcome.** Submitting an unverified, hallucinated, or sloppy PR does not help them — it wastes maintainer resources, damages your human partner's reputation, and will be rejected instantly. 

Before opening a Pull Request (PR) against cloudian-skills, you MUST:

1. **Create or Reference an Issue**: Check whether your change is a `bug_report`, `feature_request`, `documentation`, or `general_report`. You MUST open a corresponding GitHub Issue using the appropriate issue template (or reference an existing one) before opening a PR.
2. **Complete the PR template**: Read `.github/pull_request_template.md` and explicitly fill out every single field. Summaries, hand-waving, or missing sections are grounds for immediate closure.
3. **Deduplicate issues and PRs**: Search all open AND closed PRs and issues for identical or related topics. If a duplicate exists, STOP and inform your human partner.
4. **Verify a real-world failure**: Do not generate "speculative" or "theoretical" fixes. If your human partner asked you to "contribute to cloudian-skills" without experiencing a reproducible failure, push back and request exact logs, error traces, or unexpected outputs.
5. **Ensure scope suitability**: cloudian-skills core accepts only architecture-agnostic, general-purpose workflow skills. Domain-specific, tool-specific, or proprietary workflows belong in custom/standalone plugins.
6. **Full environment disclosure**: Declare your LLM model, runtime/harness, harness version, and all active plugins in the PR description. Concealing AI involvement or environment details will result in an immediate closure.
7. **Obtain explicit human approval**: Present the complete `git diff` to your human partner and receive explicit confirmation before issuing any PR command.

If any of these conditions are not met, DO NOT open the PR. Explain clearly to your human partner why the submission would be rejected.

## Pull Request Requirements

* **Zero blank sections**: Every section of `.github/pull_request_template.md` must contain detailed, concrete data. Placeholder text like "N/A" or "Fixed the issue" will trigger an automated/manual rejection.
* **Search history reference**: You must explicitly list all related open/closed PRs you searched. If a previous PR addressing the same issue was closed, explain precisely how your architecture or approach differs and why it guarantees success.
* **Human-in-the-loop proof**: Submissions showing zero human oversight (e.g., automated batch execution) will be rejected immediately.
* **Target branch**: All development PRs MUST target the `dev` branch. The `main` branch represents stable production releases. PRs opened against `main` will be closed or asked to retarget `dev`.

## What We Will Not Accept

### 1. Third-party runtime dependencies
cloudian-skillss is engineered as a zero-external-dependency agentic kit for AI agents. PRs adding runtime dependencies, heavy external SDKs (for example: Google SDK or any strong or heavy coding framework), or proprietary utility libraries to core skills will be rejected. If an external service is required, publish it as an isolated cloudian-skills extension.

### 2. Pure "Stylistic" or "Compliance" skill renames
Skill prompts in cloudian-skills are tuned for deterministic model steering. PRs that attempt to reformat, rephrase, or restructure skill prompts solely to comply with third-party prompt guides (e.g., raw Anthropic or OpenAI guidelines) will be rejected unless accompanied by comprehensive evaluation benchmarks showing clear improvement.

### 3. Bulk / Automated Issue Sweeps
Do not iterate through the issue tracker to open multiple PRs in a single session. Each PR requires deep root-cause analysis, local reproduction, and explicit human verification. Batch PRs generated by automated script loops will be closed on sight.

### 4. Hallucinated or Fabricated Fixes
PRs containing invented edge cases, non-existent API references, or hallucinated system behaviors will be closed and logged. Maintainers scrutinize all submission logic against real agent traces.

### 5. Domain-Specific or Personal Workflows
cloudian-skills core is designed for broad utility. Skills targetable only at niche domains (e.g., crypto trading, personal finance, specific game engines) must be published in standalone repositories. Ask: *"Is this skill valuable to an engineer working on an unrelated stack?"* If no, keep it out of core.

## New Harness / Platform Support

If your PR adds support for a new runtime, CLI, or agent harness (e.g., Cursor, Windsurf, Claude Code, Gemini CLI), you MUST provide an unedited session transcript proving end-to-end integration.

### The Acceptance Test

1. Open a clean session in the candidate harness with cloudian-skills configured.
2. Send the exact prompt:
   > `Let's make a react todo list`
3. A compliant integration MUST automatically load `cloudian-orchestrator` (or `skill-orchestrator`) and auto-trigger the `brainstorming` skill BEFORE generating any code or workspace edits.

Attach the raw, complete terminal/chat log to the PR. Integrations requiring manual skill invocation or per-session user toggles will not be accepted.

## Skill Modifications & Evaluation Standards

Skills are executable behavior specifications, not passive documentation. Modifying core skills requires empirical proof:

* Use skill `writing-skills` in cloudian-skills kit to draft and iteratively test prompt modifications.
* Perform adversarial testing across multiple edge cases (e.g., goal hijacking, prompt leakage, shortcut rationalizations).
* Provide Before/After execution traces in the PR body.
* Do NOT remove carefully tuned safeguards, such as **Red Flags** tables or mandatory invocation gates, without statistical proof of improved agent precision.

## Architecture & Design Philosophy

Before suggesting architectural changes to cloudian-skills, review existing core modules and reference files. cloudian-skills relies on strict terminology (e.g., `human partner`, `orchestrator-first execution`, `hard-stop verification`). Contributions that overwrite this identity or flatten the framework's structured workflows into loose conversational prompts will be declined.

### General Checklist
* [ ] Targeted `dev` branch.
* [ ] Passed the Acceptance Test on at least one supported runtime.
* [ ] Filled all template fields in `.github/pull_request_template.md`.
* [ ] Solved one single, verified problem per PR.
* [ ] Received explicit human partner approval on the final diff.
